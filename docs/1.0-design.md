# Readability 1.0 — architecture design

> Written during planning for #71. The prototype it refers to (`design/proto/`) was a
> throwaway and isn't committed. Decisions taken on top of this doc: section 9 pushback
> items 1, 2, 5, 6, 7 and 8 are accepted; the conformance suite now compares text trimmed
> and reports a separate strict `attributes` check (4.1).

## As built

What the implementation does differently from the plan below (the rest still describes it):

- **Templates**: only HTML-namespace `<template>`s are made childless at load; one inside SVG or
  MathML is an ordinary element (`DOM.from_lazy/1`), as in a DOM.
- **Grouped order**: `DOM.find_all/2` is document order. JSDOMParser's `_getAllNodesWithTag`
  groups multi-tag results by tag, but every multi-tag snapshot Readability.js iterates makes
  local decisions or counts, so the order can't show. The DOM contract (3) has one traversal
  combinator, `remove_preorder/5`: `remove_reverse` and `map_elements` (and grouped-order
  variants) ended up unused. Reverse-order removals are bottom-up passes in their own modules
  (`Clean.Conditional`).
- **Fused passes**: `_prepArticle` runs as three fused passes around the five
  `_cleanConditionally` passes (`Clean` moduledoc), and `_postProcessContent` as one pre-order
  pass (`PostProcess` moduledoc).
- **Spawned worker**: `article/2` runs in a short-lived linked process whose `min_heap_size` is
  the input size in words for inputs up to 2 MB (option `:spawn`, default on): the GC cost
  measured in 8 goes away. Larger inputs get the default heap (`Readability.Worker`).
- **Depth limit**: a binary is parsed with `max_depth: 1000` (option `:max_depth`); deeper input
  returns `{:error, :too_deep}`. Other LazyHTML limits are set by parsing to a `%LazyHTML{}`
  yourself.
- **URL subset**: no IDNA/Punycode and no IPv4 number parsing; domains are percent-decoded and
  ASCII-lower-cased, otherwise kept as written. IPv6 uses `:inet.parse_ipv6strict_address/1`.
  Every URL in the test pages still resolves as in Node.
- **Size**: about 6k lines in `lib`, 4.1k without comments and blank lines (3.3k planned).

Scope: in-memory DOM representation, traversal strategy, module layout, porting rules, caching,
regex handling, staging. Prototype code and raw results are in `design/proto/` (see Appendix).
All numbers are medians on Elixir 1.20.4 / OTP 29.1.2, Apple silicon, one fresh process per
sample, unless a different OTP is named.

## 0. TL;DR

1. **Representation: nested tuples, not a flat table.** Internal node is
   `{tag, attrs, children, stats}`; text nodes stay plain binaries; comments are dropped at load.
   `stats` is a bottom-up text aggregate (`nil` before the grab walk, always present after it).
2. **The representation is not the main lever.** Nested recursion, a zipper and a flat map table
   walk a 9.9k-element page in 6.4 / 6.3 / 7.5 ms. What moves the total is how often text is
   rescanned (up to 3.5× on the algorithm) and how class/id strings are matched (3× on the walk).
3. **Cache text aggregates in the node, bottom-up.** Scoring drops from 27.5 ms to 2.0 ms on
   wikipedia-2 and from 2.2 ms to 0.06 ms on medium-1.
4. **No PCRE on per-node paths.** The `unlikelyCandidates && !okMaybe` test costs 4.4–6.5 µs per
   element with `:re` on every OTP, 0.38 µs with a compile-time generated matcher. Cold regexes
   are compiled once at runtime into `:persistent_term`; never module attributes, never `~r`
   literals on warm paths.
5. **Own serializer** (HTML-standard fragment serialization), not `LazyHTML.Tree.to_html`.
6. **Golden traces from Readability.js** (dev-time Node script, no npm deps) are what makes the
   stages independently testable and parallelizable. `expected.html` alone is too coarse.

## 1. What the prototype measured

### 1.1 Setup

Corpus: the 130 test pages (25.7 MB; median 113 KB / 621 elements, p90 459 KB / 2038 elements,
max 9888 elements). Benchmarks ran on eight of them.

"Lite algorithm" = the grab walk (visibility, unlikely-candidate removal with the table/code
ancestor check, empty-container removal, DIV phrasing wrapping, single-P unwrapping, DIV→P),
the complete scoring loop (ancestor propagation, class weights, link density, top-5 insertion)
and serialization of the top candidate. Not included: byline and duplicate-title handling,
top-candidate refinement, sibling joining, `_prepArticle`, `_postProcessContent`, metadata.

Six implementations of that same algorithm were written and produce byte-identical output on
all eight pages: nested/rescan, nested/cached, flat map, flat `:array`, flat process dictionary,
flat ETS. The zipper implements the walk only and yields the identical tree.

Reading it:

- Traversal mechanics barely differ. The walk is dominated by predicates (keyword matching,
  attribute lookups, text scans), not by how nodes are reached.
- Flat map is 8–40 % slower than nested at equal scanning policy; ETS is 30–100 % slower.
  The process dictionary is within 1–18 % of nested but is impure and still needs a build pass.
- The flat variants here are the best case for flat: they recurse over child-id snapshots and
  rebuild each child list once. A mechanical `Dom.remove(node)` port would be slower.
- Caching aggregates is worth 1.2–3.5× on the algorithm (2.3× on wikipedia-2, 3.5× on medium-1,
  least on pages with little article text), because a literal port scans each text byte once per
  enclosing candidate. On medium-1, 18 nested candidates each rescan the same 32 KB of text.
- Heap: wikipedia-2 raw tree 3.2 MB, nested with stats 3.8 MB, flat map 3.6 MB. Not a
  differentiator.

### 1.4 Text scanning (ns per byte)

| | ns/byte |
|---|---:|
| normalized-length scanner, state-machine style | 3.3 |
| bottom-up summary scanner (non-ws units, ws runs, edge flags, commas) | 2.5 |
| naive `String.trim` → `Regex.replace(~r/\s{2,}/)` → `String.length` | 15.9–24.7 |
| same summary scanner with a forwarding helper between clauses | 11.8 |

- The BEAM does roughly 300–400 MB/s on a hand-written binary loop. One pass over wikipedia-2's
  448 KB of text is ~1.3 ms, so pass count matters.
- The last row is a real trap: a helper that receives the rest-binary and only passes it on
  ("does not begin with a suitable binary match") silently costs 4.7×. Every state function must
  itself start with a binary match. `ERL_COMPILER_OPTIONS=bin_opt_info` shows it; the scanner
  module should be compiled with that flag in CI and fail on `NOT OPTIMIZED`.
- The naive version is also wrong, not just slow (see 4.2: whitespace class, UTF-16 length).
- A random property check (20 000 cases, mixed JS whitespace, astral and BMP characters) found
  0 mismatches between the streaming scanner, the composed bottom-up summary and a JS-semantics
  reference.

### 1.5 Matching class/id strings

Test: `unlikelyCandidates.test(s) && !okMaybeItsACandidate.test(s)` over the 10 190 elements with
a class or id across the eight pages (19 686 elements in total; 48 % have neither). ns/element:

| strategy | OTP 27 | OTP 28 | OTP 29 |
|---|---:|---:|---:|
| `~r/.../i` literal in the function body | 6503 | 5124 | 4886 |
| `Regex` from `:persistent_term` | 6533 | 4664 | 4499 |
| `:re.run` on the raw pattern | 6444 | 4589 | 4440 |
| `:binary.match`, Aho-Corasick pattern from `:persistent_term`, ASCII-lowercased input | 292 | 287 | 292 |
| compile-time generated BEAM matcher, ASCII-lowercased input | 400 | 383 | 383 |
| per-document memo over `:re.run` | 2721 | 2019 | 1942 |

- PCRE without JIT tries 30 alternatives at each of ~13 positions. That is the cost, on every OTP.
- At pipeline level, PCRE for the four class/id regexes makes the walk 19.3 ms instead of 6.4 ms
  on wikipedia-2 and 1.45 ms instead of 0.42 ms on medium-1. End to end: 41.1 vs 26.9 ms and
  2.56 vs 1.36 ms.
- The generated matcher agreed with the real regexes on all 3516 distinct class/id strings in
  the sample plus hand-made edge cases, for all four patterns (including the anchored `hid`
  alternatives of `negative`).
- `:binary.compile_pattern/1` for the 30 words takes 106 µs, so compiling per call is out, and
  the compiled pattern holds a reference, so it cannot live in a module attribute either.
- Even a trivial regex (`^#.+`) is 390–450 ns per `Regex.match?`; the equivalent binary pattern
  match is 10 ns.

### 1.6 Other measurements

- **Serialization** of an 869 KB article: binary append with per-byte escaping 5.3 ms;
  iodata with a `:binary.match` prefilter 3.5 ms; `LazyHTML.Tree.to_html` 4.6 ms.
- **NIF-side navigation**: five `parent_node` + `tag` + `attribute` hops for the 386 scoreable
  nodes of wikipedia-2 take 3.8 ms (`parent_node` and `query` are dirty NIFs, so every call hops
  schedulers). The whole Elixir scoring pass takes 2.0 ms. On pixnet it is 3.4 ms vs 0.17 ms.
- **`readerable?` with LazyHTML queries only**: 130/130 pages match `expected-metadata.json`.
  Over all pages the queries cost 13 + 6 ms and `text/1` 13 ms, against 73 ms for `to_tree`
  alone. My prototype totals 83 ms because it trims with `String.trim` and converts to UTF-16;
  with the binary scanners I expect about half of `to_tree`. Not yet measured.
- **Tag membership**, 200k checks: generated function heads 3.3 ms, `tag in @list` 9.9 ms,
  `MapSet` 11.1 ms.
- **Readability.js itself**: 116 of 130 pages succeed on the first attempt, 5 need two, 1 needs
  three, 8 run all four (7 of those are tiny synthetic pages that exhaust the flags).

### 1.7 Verdict on the five options

| option | verdict | why |
|---|---|---|
| 1. Nested tuples, recursive rewrites | **Chosen**, with a 4th slot for aggregates | Fastest or tied on every phase; no build pass; ancestors and child order come free from the recursion; aggregates compose bottom-up naturally. Needs an identity scheme for candidates (2.3). |
| 2. Flat table, integer ids | Rejected | +8–40 % at equal work, a 0.1–1.2 ms build pass, a rebuild pass before output, and cached aggregates need explicit invalidation up the parent chain. Its one real advantage is mechanical porting. Golden traces buy the same safety without the cost. |
| 3. Zipper | Rejected | Same speed as recursion for the walk, but no node identity and no bottom-up results, so scoring and `_cleanConditionally` gain nothing. |
| 4. NIF-side with CSS queries | Rejected for the algorithm, candidate for `readerable?` | LazyHTML documents are immutable and nodes have no identity across calls; per-call overhead exceeds doing the work in Elixir. |
| 5a. ETS / process dictionary | Rejected | ETS is the slowest variant. The process dictionary is fast but leaks state into the caller's process and loses free retries. |
| 5b. Per-node cached text aggregates | **Chosen** | The largest measured win. |
| 5c. Bottom-up single-pass score propagation | Not now | It changes the order of float additions and of candidate creation, both observable through tie-breaks. The straightforward scoring pass costs 2 ms on the largest page. |

## 2. Recommended representation

### 2.1 Node shape

```elixir
@type tree  :: [node_]
@type node_ :: el | text
@type text  :: binary                      # never merged, never normalized
@type el    :: {tag :: binary, attrs :: [{binary, binary}], children :: [node_], stats | nil}

# bottom-up aggregate over the element's whole subtree
@type stats :: {
  nonws      :: non_neg_integer,  # UTF-16 units that are not JS whitespace
  runs       :: non_neg_integer,  # maximal JS-whitespace runs
  lead       :: 0 | 1,            # text starts with whitespace
  trail      :: 0 | 1,            # text ends with whitespace
  commas     :: non_neg_integer,  # ","
  xcommas    :: non_neg_integer,  # the other eight comma code points of REGEXPS.commas
  link_len   :: non_neg_integer,  # sum of inner-text lengths of <a> without a "#…" href
  hash_links :: non_neg_integer   # number of <a> with a "#…" href
}
```

- Tags are lower-case binaries exactly as LazyHTML returns them (SVG names keep their case).
  Converting to atoms would cost a full copy at each end for no measured gain.
- `inner_text_length(node) = if nonws == 0, do: 0, else: nonws + runs - lead - trail`. This is
  exactly `textContent.trim().replace(/\s{2,}/g, " ").length`: every whitespace run contributes
  one character, leading and trailing runs none. Concatenation merges adjacent runs:
  `runs = a.runs + b.runs - min(a.trail, b.lead)`.
- `stats == nil` means "not computed": the state of every node between load and the grab walk.
  Accessors fall back to a scan. After the walk, every element has stats, and all later code
  builds elements through `DOM.el/3`, which recomputes from the children (O(children), rescans
  only direct text children).
- `DOM.put_attrs/2` and `DOM.put_tag/2` keep stats (recomputing only when an `<a>` is involved).
- One internal marker exists: `{:data_table, boolean}` as an atom-keyed attribute on `<table>`,
  set by `_markDataTables` and stripped at the end of `_prepArticle`. Atom keys cannot collide
  with parsed attributes; the serializer raises on one, so a leak fails loudly.

### 2.2 Lifecycle

```
html ─ LazyHTML.from_document ─ to_tree ─ DOM.from_lazy (drop comments, 4-tuples, stats=nil)
     ─ Prep (noscript images, JSON-LD read, drop script/noscript/style, <br> chains, font→span)
     ─ Metadata
     ─ Grab attempt(flags): walk → tree with stats → score → select → article subtree
         ─ Clean (_prepArticle) → length check → retry with fewer flags on the SAME prepared tree
     ─ PostProcess ─ Serializer ─ %Article{}
```

The prepared tree is immutable, so the retry loop needs no copy and no re-parse (JS re-parses
`page.innerHTML`). Stats are produced as a by-product of the walk's rebuild, only for nodes that
survive it; removed subtrees are never scanned.

### 2.3 Identity, parents, siblings

Only the candidate phase needs identity. Use the **reversed child-index path in the post-walk
tree**: `[i_n, …, i_1, i_0]`, built as `[i | parent_path]` during recursion.

- The parent's identity is `tl(path)`; all ancestors are the successive tails; a sibling is
  `[j | tl(path)]`. No parent pointers, no ids in nodes.
- Indexes count all child nodes, text included, in the output tree.
- Candidates: `%{path => {score, node}}` plus an insertion-order list.
- Ancestor context everywhere else is the recursion stack: a list of `{tag, attrs}` frames,
  nearest first. `_hasAncestorTag(node, tag, 3)` inspects the first **four** frames (the JS
  depth check is off by one); `maxDepth = -1` inspects all of them.
- Paths are valid for one attempt, until the article subtree is assembled. Nothing later uses them.

The scoring pass is a separate pre-order traversal of the finished walk output. That works
because `elementsToScore` is exactly "all elements of the post-walk tree whose tag is in
`section,h2,h3,h4,h5,h6,p,td,pre`, in document order": the two extra pushes in the JS loop
(DIV→P and single-P unwrapping) both produce `p` elements at the same pre-order position.

## 4. Porting faithfully

### 4.1 What the oracle actually checks

- `expected.html` is the output of Readability.js on **JSDOMParser**, then `js-beautify`. Where
  jsdom and JSDOMParser differ, follow JSDOMParser. Both pass upstream, so no test depends on a
  difference.
- The JS test serializes the result, pretty-prints it, **re-parses** it and walks both DOMs in
  document order, skipping whitespace-only text nodes, comparing: node type; for elements
  `localName`, `id`, `className`; for text, content with `\s+` collapsed.
- Attributes: the loop compares the **number** of attributes only. The value comparison indexes
  `.name` on a string and ends up comparing `null` with `null`.
- Consequences for our harness:
  1. Compare `LazyHTML.to_tree(from_fragment(our_content))` with the same for `expected.html`.
     Never compare the in-memory tree: Readability produces trees that do not survive
     serialization (block elements inside `<p>`), and the re-parse hides that on both sides.
  2. `js-beautify` moved whitespace at tag boundaries in `expected.html`. Upstream pretty-prints
     both sides; we cannot. Compare text nodes trimmed and collapsed, and accept that
     inter-element spacing is not checked by this suite.
  3. Compare attribute names and values as a separate, stricter metric with its own failure list.
- Pass `classes_to_preserve: ["caption"]` and `url: "http://fakehost/test/page.html"`, as upstream does.

### 4.2 Semantics that must match exactly

| JS | Elixir trap | do this |
|---|---|---|
| `.length`, `substring`, thresholds like `< 25`, `/ 100`, `< 500` | `String.length` counts graphemes; `byte_size` counts bytes | UTF-16 code units: one per code point, two above U+FFFF. Hand-written scanner |
| `\s`, `trim()`: TAB LF VT FF CR SP, U+00A0, U+1680, U+2000–200A, U+2028, U+2029, U+202F, U+205F, U+3000, U+FEFF | `String.trim` and PCRE `\s` with `u` include U+0085 and exclude U+FEFF; PCRE `\s` without `u` is ASCII only, so `&nbsp;` is not whitespace | one whitespace class in `Text`, used everywhere |
| `$` matches only at end of input | PCRE `$` also matches before a final `\n`. `hasContent = /\S$/` is false for `"foo\n"` in JS, true in PCRE | hand-written, or `\z` |
| `.` excludes `\n \r U+2028 U+2029` | PCRE `.` excludes only `\n` | hand-written for `hashUrl` |
| `/i` without `u`: ASCII-only folding for ASCII patterns | fine | ASCII lower-case then match |
| `/iu` (`adWords`, `loadingWords`) | needs Unicode folding | real regex with `iu`, behind a length prefilter |
| `str.split(/\s+/).length` (`wordCount`) | `String.split/1` drops empty leading/trailing parts | count whitespace runs + 1; `""` gives 1 |
| `\W`, `\b`, `\w`: ASCII | same in PCRE without `u` | `tokenize` splits on non-`[A-Za-z0-9_]`, so every non-ASCII letter is a separator |
| `toLowerCase()` | | `String.downcase/1` before tokenizing |
| float score arithmetic and comparisons | reordering additions changes the last bit, visible through `>` ties and `>= 0.75` | same operations in the same order: contributions in document order, `score / divider`, `score * (1 - density)` |
| `linkLength += len * 0.3` in document order | a pre-aggregated float differs | integer `link_len` when `hash_links == 0`; otherwise an ordered walk over the `<a>` descendants |
| `parseInt(x, 10)`, `x \|\| 1` for rowspan/colspan | | prefix integer parse; `NaN` and `0` become 1, negatives stay |
| `options.x \|\| DEFAULT` | 0 means "default" in JS | validate as positive integers, document it |
| `tagName` upper-case, `localName` lower-case | | compare lower-case everywhere |
| adjacent text nodes are distinct nodes | merging changes `childNodes.length === 1` checks | never merge binaries in a child list |
| `node.style.display` | CSSOM in jsdom, a `;`/`:` split in JSDOMParser | JSDOMParser's split: first declaration whose trimmed name equals the property |
| `new URL(u, base).href` | `URI.merge/2` is RFC 3986: no percent-encoding, no host lower-casing, no `\`→`/` | `Readability.URL`, table-tested against Node |
| `doc.baseURI` vs `doc.documentURI` | | honour the first `<base href>`; hash links are left alone only when the two are equal |
| comments | LazyHTML keeps them | drop at load (JSDOMParser discards them; the jsdom test run strips them) |
| `<noscript>` content | | Lexbor parses it as elements, like jsdom without scripting. Verified |
| `<template>` | LazyHTML exposes the template content as children; a DOM does not | make it childless at load. Two test pages contain one |

### 4.3 Translating the iteration idioms

Readability.js uses three patterns. Each has an exact structural equivalent; choosing the wrong
one is the most likely way to introduce a silent divergence.

1. **`_getNextNode` / `_removeAndGetNext` loop** — pre-order; the decision about a node is made
   before its descendants are visited and sees them unprocessed. Equivalent: recursion that
   decides first, then maps over the children left to right, threading an accumulator.
   Used by: the grab walk, `_cleanMatchedNodes`, `_simplifyNestedElements`, the byline
   `itemprop=name` search.
2. **`_removeNodes(_getAllNodesWithTag(e, tags), fn)`** — a static snapshot iterated in
   **reverse document order**. When `fn` runs on a node, all its descendants and everything after
   it have already been processed, and none of its ancestors has. Equivalent: process children
   right to left, rebuild the node, then decide. The node is always still attached at that point.
   Used by: `_clean`, `_cleanConditionally`, `_cleanHeaders`, the empty-paragraph removal.
3. **`_forEachNode(snapshot, fn)` in document order with local edits** — nodes detached by an
   earlier iteration are still visited but have no siblings or parent. Each use needs its own
   argument:
   - `_replaceBrs`: rewrite each child list left to right. A following sibling is tested for
     phrasing content in its **original** state, then recursed into when emitted. `font` is still
     `font` at that time and is not phrasing content, so convert font→span afterwards. The second
     and later `<br>` of a chain are removed and their own iteration is a no-op.
   - `_unwrapNoscriptImages`: fold each child list left to right; "previous element sibling" is
     looked up in the already-emitted output.
   - `br` before `p` in `_prepArticle`: only the `<br>` immediately preceding the `<p>` (ignoring
     whitespace text) is removed, not a chain.
   - single-cell tables: top-down. Replace the table by its retagged cell, then continue into the
     replacement, where inner tables are still unprocessed.

Order constraints inside `_prepArticle` that forbid fusing passes:

- `_markDataTables` reads the tree before anything is removed; its result must be stored, not
  recomputed later.
- `_cleanConditionally("form")`, `("fieldset")` run before the first `_clean` group.
- `_cleanMatchedNodes` (share elements) reads `textContent.length` after the first `_clean` group
  (object, embed, footer, link, aside) and before the second (iframe, input, textarea, select, button).
- `table`, `ul`, `div` conditional cleaning are three passes: the `ul` decision must see `div`
  descendants that the `div` pass has not yet removed.
- Within each group the removals are independent of each other and may be fused. Do that in the
  performance stage, not in the first port.

### 4.4 Quirks to preserve, not fix

- `_clean`: `element.tagName === "object"` compares an upper-case value with a lower-case literal
  and is never true. The `innerHTML` video check is dead code; keep it dead. Same in
  `_cleanConditionally`.
- `_isValidByline` computes `textContent.trim().length` for every node. Evaluate it only when the
  rel/itemprop/class test passed; the result is the same.
- `_articleByline` survives across attempts: once found in attempt 1, later attempts neither look
  for nor remove a byline node.
- On the final fallback (all four attempts too short) the returned content is the longest
  attempt's, but `dir` is derived from the **last** attempt's top candidate.
- `_attempts.sort` is stable and descending, so the earliest attempt wins a tie.
- The `<html>` element is never initialized as a candidate (its parent has no `tagName`), so
  `<body>` is the outermost possible candidate.
- `_hasSingleTagInsideElement` uses `/\S$/`: a text node ending in whitespace counts as empty.
- `_isElementWithoutContent` compares the number of element **children** with the number of
  `br` + `hr` **descendants**.
- The wrapper `<div>` created when no candidate exists is itself a `div` descendant of the
  article and goes through `_cleanConditionally("div")` before it receives its id and class.
- `contentScore` inside `_cleanConditionally` is the constant 0.
- JSON-LD: only the first script that yields metadata is used; a parse error is swallowed.

### 4.5 Where a literal port is slow, and what replaces it

| JS does | cost | we do |
|---|---|---|
| `textContent` of every node in the walk (byline check) | O(n · depth) bytes | lazy evaluation |
| `_getInnerText` / `_getLinkDensity` per candidate and per `_cleanConditionally` target | each byte scanned once per enclosing candidate: 27.5 ms on wikipedia-2 | O(1) from stats |
| `getElementsByTagName(x).length` for p, img, li, input, embeds, headings, lists in `_cleanConditionally` | O(n · depth) | counts returned bottom-up by the same pass that removes |
| `_hasAncestorTag` parent walks | cheap in JS, awkward here | ancestor frame stack |
| `_getAllNodesWithTag` + loop, ten `_clean` calls in a row | one traversal each | one recursive pass each at first; fuse independent ones later |
| `page.innerHTML = pageCacheHtml` on retry | serialize + re-parse | reuse the immutable prepared tree |
| regex on `className + " " + id` per node | 4.4–6.5 µs | generated matcher, 0.38 µs; skip entirely when both are absent |
| build the inner-text string to take `.length` | allocation + regex | length-only scanners; build a string only where the content is read |
| `tmp.innerHTML = noscript.innerHTML` | re-parse | reuse the noscript's children (copying is free) |

## 5. Caching and complexity

- **Invariant**: after `Grab.Walk`, `inner_text_length`, both comma counts and (without `#`
  links) link density are O(1) for every element.
- **Byte scans per attempt**: one summary scan (2.5 ns/byte) of the text that survives the walk,
  plus short-circuiting scans on unprocessed subtrees inside the walk (`blank?`, the single-P
  link density, byline text), plus rescans of the direct text children of elements rebuilt later.
  Bulk text sits in leaf-ish elements that later passes rarely rebuild.
- **Combinators must return the original node when nothing changed.** Otherwise each of the ~15
  `_prepArticle` passes re-aggregates every element. This lives in three combinators, not in
  every pass.
- **Class weight / unlikely test**: computed on demand with the generated matchers. A
  per-document memo keyed by the class string is a possible later optimization (3516 distinct
  strings among 10 190 in the sample); measure first.
- **Scores**: a map with a few hundred path keys. On the largest page the whole scoring pass is
  2.0 ms; switching to integer keys is a micro-optimization for later.
- **`_cleanConditionally`**: a dedicated recursive function returning `{node | :removed, counts}`
  where `counts` carries p, img, li, input, embeds, heading length, textish length, list length
  and a has-data-table flag. Length, commas and link density come from stats.
- **`adWords` / `loadingWords`**: only run when the normalized length is ≤ 13 (the longest
  alternative); only then build the string.
- **Image-extension tests** on attribute values: generated matcher as a prefilter, the exact
  regex only on a hit.
- **Outputs**: text binaries from `to_tree` are resource binaries that keep the whole Lexbor
  document alive (about 15× the HTML size, per LazyHTML's docs). `content` and `text_content` are
  freshly built; every other returned string (title, byline, excerpt, site name, published time,
  lang, dir) must go through `:binary.copy/1`.

## 6. Regex strategy

Facts (measured or read from the Elixir 1.20.4 source):

- OTP 28+ compiled patterns contain a reference, so they can no longer be embedded in compiled
  code. Elixir 1.17/1.18 fail to escape them (the bug fixed in #69). Elixir 1.19+ works around it
  in `Regex.__escape__/1`, which serves both `~r` literals and module attributes:
  - on OTP 28.1+ it emits `:re.import(exported)`, executed **at every evaluation**: 717 ns vs
    393 ns for a cached pattern on a trivial regex;
  - on OTP 28.0 it emits `:re.compile(source, opts)` at every evaluation. Compiling one of the
    class/id patterns takes roughly 110–270 µs.
- On OTP 27 a literal is a constant and free.
- PCRE is slow on wide alternations on every OTP (1.5).

Rules:

1. **Per-node and per-text-node tests use no regex.** Whitespace, `hasContent`, `hashUrl`, commas:
   binary pattern matching in `Text`. Keyword sets (`unlikelyCandidates`, `okMaybeItsACandidate`,
   `positive`, `negative`, `byline`, image extensions): functions generated at compile time from
   the word lists, applied to an ASCII-lower-cased string. `lower/1` returns its argument
   unchanged when there is nothing to change. No global state, identical on every OTP.
2. **Prefilter, then the exact regex**, where the pattern has structure: `shareElements` (substring
   `share` first), the lazy-image patterns, `b64DataUrl` (prefix `data:` first), `videos` (only on
   object/embed/iframe attributes), `adWords`/`loadingWords` (length first).
3. **Cold regexes** (title separators, meta `property`/`name` patterns, JSON-LD types, `srcsetUrl`,
   entity unescape, and the exact regexes of rule 2) are compiled with `Regex.compile!/2` on first
   use and stored as one tuple under one `:persistent_term` key. That is a native pattern for the
   running VM, compiled once, the same code on OTP 27, 28.0, 28.1+ and 29. Two processes racing on
   the first call write the same value.
4. **Never** a `Regex` in a module attribute. No `~r` literal outside tests. Enforce with a Credo
   check or a grep in CI.
5. A user-supplied `allowed_video_regex` is used as given.
6. Every generated matcher has a test asserting agreement with the JS-equivalent regex over the
   class/id strings of all test pages plus edge cases.

Translation hazards when writing the cold regexes: `$` → `\z`; no `u` flag unless the JS regex
has one; `\s` only where the ASCII class is correct, otherwise the explicit JS class.

## 7. Implementation stages

Each stage has its own pass metric. "Suite" is the 130-page oracle (content, strict attributes,
and each metadata field counted separately). "Trace" is the golden-trace comparison below.

**Stage 0 — harness** (already planned), with two additions:
- `mix readability.traces`: a Node script that needs only the vendored `Readability.js` and
  `JSDOMParser.js` (no npm install; `js_stats.js` in the prototype runs this way). It wraps the
  stage functions and dumps, per page, JSON for: metadata and JSON-LD; the tree after
  `_prepDocument`; per attempt the flags, the number of elements scored, candidates with scores,
  the top candidate, the article tree before and after `_prepArticle`; the tree before and after
  `_postProcessContent`; final `textContent` and `length`. Trees are dumped as nested arrays
  `[tag, attrs, children]`, never as HTML, because these trees do not survive a re-parse.
  Output is roughly 100+ MB, so it is git-ignored and generated locally. CI runs the suite only.
- A parser-parity check: LazyHTML's tree for every `source.html` against the JSDOMParser tree
  from the trace. This tells us on day one which pages can never match and why.

**Stage 1 — foundations** (pure, unit-testable, four parallel work items once the `DOM` contract
in section 3 is agreed):
- 1a `Text`: tests are tables generated by Node for length, trim, normalize, word count,
  similarity, entity unescape; plus the property check from the prototype.
- 1b `Matchers`: agreement tests against regexes (rule 6).
- 1c `DOM` + `Serializer`: round-trip tests; stats equal a fresh recomputation after random
  edits (property test); serializer output re-parses to the same tree.
- 1d `URL`: table of every `(uri, base)` pair occurring in the test pages, expected values from
  Node's `URL`.

**Stage 2 — metadata.** Metric: title, excerpt (when not derived from content), siteName,
publishedTime, lang over 130 pages. Independent of stages 3–6.

**Stage 3 — prep.** Metric: trace equality of the tree after `_prepDocument`.

**Stage 4 — grab** (walk, score, select, retry loop with `Clean` stubbed). Metric: trace equality
for attempt 1: number of scored elements, candidate scores (exact float equality), top candidate,
article tree before `_prepArticle`. Byline joins the suite metric here.

**Stage 5 — clean.** Input is the trace's pre-`_prepArticle` tree, expected output the
post-`_prepArticle` tree, so it does not wait for stage 4.

**Stage 6 — post-process and assembly.** Input and output again from the trace. Adds excerpt
fallback, `text_content`, `length`, `dir`.

**Stage 7 — integration.** Wire stages together, options, `readerable?`, error returns. The full
suite number becomes meaningful here; `known_failures` starts and may only shrink.

**Stage 8 — performance.** Benchee against 0.13.0, profile-driven: fuse independent `_clean`
passes, iodata serializer (measured 1.5× on large output), class-string memo, NIF-side
`readerable?`, `bin_opt_info` gate.

**Parallelization.** Stage 1a–1d: four agents. Then stages 2, 3, 4, 5, 6: five agents, because
the traces give every stage its own inputs and expected outputs. Stage 4 is the largest and
riskiest; give it the strongest agent and let stage 5 start from the trace rather than from
stage 4's output. Stage 7 is one agent. The one hard serialization point is the `DOM` contract.

## 8. Risks and how to retire them early

| risk | likelihood | retire by |
|---|---|---|
| Wrong idiom translation (4.3) gives rare silent divergences | high | traces per stage; the per-function notes in 4.3–4.4 are the review checklist |
| JS string semantics leak through `String.*` or PCRE | high | single `Text` module, Node-generated tables in stage 1a; ban `String.trim`, `String.length`, `=~` in `lib/` except `Text`/`Matchers` |
| Lexbor tree differs from JSDOMParser's for some sources | medium | parser-parity check in stage 0 |
| `expected.html` whitespace noise (js-beautify) hides or fakes failures | medium | trimmed text comparison in the suite, exact comparison in traces |
| URL resolution differs from WHATWG | medium | stage 1d table |
| Float tie-breaks | low once the order is copied | exact score equality in stage 4 traces |
| Stats go stale because some code builds a tuple by hand | medium | constructor-only rule, the property test in 1c, and a debug-mode `DOM.verify!/1` run in the test suite after every stage function |
| A scanner silently loses match-context reuse | medium | `bin_opt_info` gate |
| `to_tree` is a regular (non-dirty) NIF: 6 ms on a 1 MB page on a normal scheduler | certain | cannot fix here; raise upstream, document it |
| Resource binaries retain the parsed document | certain if forgotten | `:binary.copy/1` on returned fields; a test asserting `:binary.referenced_byte_size` of each field |
| LazyHTML is a NIF: precompiled for common targets, otherwise needs a C++ toolchain, CMake and fetches Lexbor at build time | low for most users, blocking for a few | say so in the README; it replaces a pure-Elixir dependency |
| Untrusted input (deep nesting, huge documents) | medium | pass `max_depth` / `max_memory` / `timeout` through to `LazyHTML.from_document/2`; map `max_elems_to_parse` |
| Benchmark artefacts | seen during this work | measure one document per process. Sharing a heap with eight parsed pages made one variant read 963 ms instead of 52 ms |

## 9. Pushback

1. **"Algorithm on plain tuples → `LazyHTML.Tree.to_html`"** (the plan as recorded): I recommend
   against both halves. Plain 3-tuples leave nowhere to keep aggregates, which is the biggest
   measured win. `Tree.to_html` writes `<br/>`, escapes `"` and `'` in text and does not emit
   `&nbsp;`; an own serializer follows the HTML standard, is ~120 lines and is no slower.
   `from_document` and `to_tree` stay as decided.
2. **"Port first, performance afterwards"** is only half right. Pass fusion and micro-tuning can
   wait. The node shape, the constructor discipline and the no-PCRE-on-hot-paths rule cannot:
   retrofitting them touches every pass. They are cheap to adopt from the first commit.
3. **The upstream suite is weaker than it looks** (attribute count only, beautified whitespace,
   re-parse on both sides). Treating its pass rate as the fidelity metric will overstate fidelity.
   The traces are the real oracle; the suite is the regression gate.
4. **Beating 0.13.0 is not a meaningful target.** Its parser alone is 2.5–23× slower than
   `from_document` + `to_tree` (10× or more on every benchmark page above 400 KB). Useful targets: algorithm time ≤ parse + `to_tree` time on every
   benchmark page, and faster than Readability.js on JSDOMParser.
5. **`{:error, :not_readable}` as the only error** conflates "no content" with "document over
   `max_elems_to_parse`" (JS throws there). I would add `{:error, :too_many_elements}`.
6. **Accept a `%LazyHTML{}` as input** besides a binary. Callers that run `readerable?/2` and then
   `article/2` otherwise parse twice, and parsing is 14–35 % of the prototype's end-to-end time.
7. **Minimum Elixir 1.17 has no `JSON` module**, but OTP 27 has `:json`. Use `:json.decode/1` for
   JSON-LD and do not add Jason.
8. **`char_threshold: 0`** and the other numeric options silently mean "default" in JS. Mirroring
   that is surprising in Elixir; validate as positive integers instead and note the difference.
